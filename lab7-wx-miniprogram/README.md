# 校园报修助手·小程序

> 《移动应用开发》综合项目（实验七）
> 选题方向：项目九·微信小程序应用 —— 校园报修
> 作者：李春雨（学号 202305567128，计科 2 班）

## 一、做什么 / 为什么做

面向校园宿舍、教室、公共区域的报修场景，开发一个让师生「随手提交报修、跟进处理进度」的微信小程序。

核心痛点：
- 传统报修需到宿管处登记、电话沟通，记录易丢失；
- 维修进度不透明，无法及时反馈；
- 管理员缺少集中处理入口，统计不便。

本方案用小程序轻量化解决：扫码即用、提交即存、处理即通知。

## 二、核心功能

| 页面 | 路径 | 职责 |
| --- | --- | --- |
| 登录 | `pages/login/login` | 账号密码登录、微信一键登录、会话与角色写入 |
| 报修列表 | `pages/index/index` | **按角色自适应**：标签页、数据范围、操作按钮随角色变化；分页加载，点击进详情 |
| 提交报修 | `pages/publish/publish` | 表单录入（位置/楼栋/房间/手机/故障类型/描述/图片）+ 输入校验 + 订阅消息 |
| 报修详情 | `pages/detail/detail` | 申报状态标签、维修人员、不受理原因、维修记录与图片、一键拨号/复制电话 |
| 管理后台 | `pages/admin/admin` | 仅超级管理员可见，**审核报修（确认并指派师傅 / 不受理并填原因）**、删除、发送状态通知 |
| 上传维修情况 | `pages/repair/repair` | 仅维修人员可进，填写维修说明 + 上传现场图片，可「仅保存记录」或「提交并完成」 |

**审核状态机**：

```
提交报修（未处理）
   ├─ 超级管理员「审核通过」→ 已确认（指派维修人员：姓名 + 电话）
   │        └─ 维修人员「上传维修情况」→ 已处理（追加维修记录）
   └─ 超级管理员「不受理」→ 不受理（记录 rejectReason 不受理原因）
```

业务流程：`提交报修 → 写库 → 通知管理员 → 管理员审核（已确认/不受理）→ 指派师傅 → 维修人员上传维修情况 → 通知报修人 → 列表状态更新`

## 三、技术架构

```
┌─────────────────────────────────────────────┐
│  UI 层（Page）login/index/publish/detail/admin/repair│
├─────────────────────────────────────────────┤
│  Repository 层  utils/api.js（统一封装）              │
├──────────────┬──────────────────────────────┤
│  云开发优先    │  本地兜底（实验七新增）              │
│  - 云数据库    │  - wx.storage 本地缓存             │
│  - 云函数     │  - mock 种子数据                │
│  - 云存储     │  - 「我的报修」离线缓存           │
└──────────────┴──────────────────────────────┘
```

**关键设计**：

1. **统一 Repository 层**：所有数据访问走 `utils/api.js`，页面不直接调 `wx.cloud`，方便维护与切换数据源。
2. **云开发 + 本地兜底双模**（实验七完善）：`USE_MOCK_FALLBACK=true` 时，未开通云环境或调用失败自动回退到 `wx.storage` 本地数据，保证无云环境也能演示完整业务流程。
3. **本地数据保存**（任务书要求）：提交的报修同步写入 `wx.storage` 的 `my_repairs` 缓存，支持离线查看本人提交记录；管理员信息缓存到 `admin`。
4. **输入校验**：申报人/位置/楼栋/房间/故障类型/手机号正则/描述均校验，缺项给 Toast 提示。
5. **异常处理**：所有云调用 `try/catch`，失败时给用户明确 Toast 反馈，不再只 `console.log`。
6. **订阅消息通知**：提交报修给管理员发「新报修」通知，处理完成给报修人发「已处理」通知（云函数）。
7. **角色权限（三档）**：`c_role` 集合存账号/密码/角色/归属宿舍/维修人员信息，前端按 `role` 决定标签页、数据范围与操作按钮：

   | 角色 | 可见数据 | 首页标签页 | 独有操作 |
   | --- | --- | --- | --- |
   | 超级管理员 | 全部报修 | 待审核 / 已确认 / 不受理 / 已完成 | 管理员入口、楼栋筛选、审核通过（指派师傅）、不受理（填原因）、删除 |
   | 维修人员 | 指派给自己的（`workerName === 本人姓名`） | 待维修 / 已完成 | 上传维修情况 |
   | 普通用户 | 仅自己宿舍（`floor + dorm`） | 我的列表 / 已完成 | 提交报修 |

8. **审核状态流转**：`updateApply(id, patch)` 为通用更新入口，其上封装 `confirmApply`（已确认 + 维修人员姓名/电话）、`rejectApply`（不受理 + 原因）、`submitRepair`（追加维修记录，可选同时置「已处理」）。

## 四、运行方式

### 方式一：有云开发环境（完整功能）

1. 微信开发者工具导入 `d:\rain_android\wx`；
2. 修改 `miniprogram/config/index.js` 中 `CLOUD_ENV` 为你的云环境 ID；
3. 上传 `cloudfunctions/` 下的 `login`、`applyNotice`、`handleNotice` 云函数（上传并部署，不上传 node_modules）；
4. 云控制台创建集合 `c_apply` / `c_role` / `c_share`，导入 `databases/` 下的数据（`c_apply` 已含 `location / faultType / rejectReason / workerName / workerPhone / repairRecords` 等审核流字段，无需额外加字段）；
5. `c_apply` 集合权限改为「自定义安全规则」read/write true；
6. 编译运行，用 `c_role` 中的账号登录（默认 `admin / 123456` 为超级管理员），也可点「微信一键登录」按 openid 匹配角色。

> 账号体系说明：`c_role` 集合含 `account` / `password` / `role` / `name` / `phone` / `openid` 字段。
> 账号密码登录按 `account + password` 匹配；微信一键登录按 `openid` 匹配。二者可并存。

### 方式二：无云环境（本地兜底演示，实验七新增）

无需开通云开发，直接编译即可运行：
- `api.js` 检测到 `wx.cloud` 不可用或调用失败，自动回退到本地 `wx.storage`；
- 首次启动注入 5 条 mock 种子数据，覆盖 4 种状态（未处理 ×2 / 已确认 / 不受理 / 已处理），含维修人员与维修记录；
- 提交的报修写入本地 `my_repairs` 缓存；
- 管理员、登录、订阅消息、图片上传均走 mock，不影响主流程演示。

## 七、测试说明

### 边界与异常用例

| 场景 | 预期 | 实测 |
| --- | --- | --- |
| 列表为空 | 按角色显示空状态 | 种子 5 条；维修人员「待维修」可见 1 条 |
| 无云环境 | 自动本地兜底，不报错 | 关闭云开发即可验证 |
| 提交缺申报人 | Toast「请填写申报人」 | validate() 拦截 |
| 手机号格式错 | Toast「请填写正确手机号」 | 正则 `/[1][3,4,5,7,8][0-9]{9}$/` |
| 图片超 6 张 | Toast「最多上传 6 张」 | chooseImage remaining 校验 |
| 加载失败 | Toast「加载失败，请重试」 | 断网/云函数异常 |
| 详情不存在 | Toast「记录不存在或已删除」 | 删除后回退详情页 |
| 非管理员点管理 | Toast「暂无权限」 | isAdmin 判断 |
| 未登录 | 自动跳转登录页 | index/admin/repair 三重守卫 |
| 账号或密码错误 | Toast「账号或密码错误」 | 不进入首页 |
| 非管理员进 admin 页 | Toast「请先以管理员账号登录」并回登录页 | `session.role !== '超级管理员'` 守卫 |
| 非维修人员进 repair 页 | Toast「请以维修人员账号登录」并回登录页 | `session.role !== '维修人员'` 守卫 |
| 审核时无维修人员账号 | Toast「暂无维修人员账号」 | confirmApply 空列表校验 |
| 不受理未填原因 | Toast「请填写不受理原因」 | 空原因拦截 |
| 维修情况全空 | Toast「请填写维修情况或上传图片」 | repair.submit 前置校验 |
| 无维修人员可指派 | 弹窗无可选项 | seed 已含 2 名维修人员 |

### 演示步骤（答辩用）

**审核与维修主流程**

1. 登录页：点演示账号填充或手输 `admin / 123456`，以超级管理员登录；

4. 管理后台（点「管理员入口」）：
   - 对一条记录点「**审核通过**」→ 弹出维修人员列表（罗钢 / 贺强）→ 选一位 → 状态变蓝色「已确认」，卡片显示维修人员姓名与电话；
   - 对另一条点「**不受理**」→ 弹窗填写原因 → 状态变红色「不受理」，卡片显示不受理原因；
5. 退出登录，用 `luogang / 123456` 以维修人员登录：首页只有「待维修 / 已完成」两个 Tab，仅显示指派给自己（罗钢）的任务；

7. 详情页：可见申报状态标签、维修人员（含一键联系/复制）、不受理原因、维修记录（内容 + 图片 + 时间 + 操作人）。

**权限与兜底演示**

8. 用 `wlx / 123456`（普通用户）登录：只看到 2栋104 的记录，首页无「管理员入口」与楼栋筛选；
9. 直接访问 admin 页 → 提示「请先以管理员账号登录」并跳回登录页；访问 repair 页同理；
10. 无云演示：关闭云开发，重启小程序，验证本地兜底正常（种子 5 条覆盖 4 种状态）。

## 十、答辩四问自检

- **数据在哪里？** 云数据库 `c_apply` / `c_role` + 本地 `wx.storage`（local_apply/local_role/my_repairs/admin/mock_seeded_v2）。
- **状态在哪里？** Page 的 `data` + `setData`；业务状态（未处理/已确认/不受理/已处理）持久化在报修记录 `status` 字段；登录态在 `wx.storage` 的 `userInfo`。
- **事件从哪里来、到哪里去？** 用户操作 → Page 方法 → `api.js` → 云/本地 → 回调 `setData` 渲染。
- **错误在哪里处理？** `api.js` 每个方法 `try/catch` + 页面 Toast 反馈，云失败自动回退本地。
